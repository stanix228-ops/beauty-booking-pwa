## 2. Проверка архитектурных инвариантов

1. **Мультитенантность в одном билде и инстансе:**
   - Все зависимые таблицы и запросы строго содержат `tenant_id` с составными внешними ключами.
   - Маршрутизация `/s/:slug/` и `/s/:slug/owner/` функционирует из единого статического бандла.
2. **Конвейер `business.json`:**
   - Работают скрипты `tenant:new`, `tenant:validate`, `tenant:publish`, `tenant:verify`.
   - Переиздание конфигурации (`tenant:publish`) использует `ON CONFLICT DO UPDATE` и **никогда не удаляет** существующие записи, клиентов или историю.
3. **Исключение перекрытий (No Overbooking) через PostgreSQL `EXCLUDE`:**
   - В миграции `20261003_init_nail_schema.sql` таблица `resource_occupancies` использует `EXCLUDE USING gist (tenant_id WITH =, resource_id WITH =, time_range WITH &&)`.
   - Блокирует одновременное занятие одного мастера или рабочего места двумя клиентами.
4. **Атомарные транзакции на стороне PostgreSQL:**
   - Функции `create_booking_atomic`, `reschedule_booking_atomic`, `cancel_booking_atomic`, `block_master_time_atomic`.
   - Клиент никогда не передает цену, длительность или внутренние ID ресурсов.
   - При сбое переноса исходная запись сохраняется без потерь.
5. **Беспарольный доступ для клиентов:**
   - Клиент получает защищенный токен в URL (`/s/:slug/b/:token`).
   - В БД сохраняется только криптографический SHA-256 хэш токена.
   - Владелец авторизуется через Supabase Auth (`/s/:slug/owner/login`) с membership-проверкой.
6. **Строгие RLS и изоляция данных:**
   - Роль `anon` имеет доступ только к публичным данным тенанта (услуги, мастера, свободные слоты через RPC).
7. **AI-ассистент с безопасным Tool Loop:**
   - Edge Function `ai-chat` с настраиваемыми `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`.
   - Модель не имеет прямого доступа к SQL и tenant_id.
   - Атомарный счетчик токенов и бюджета в таблице `rate_limit_usage`.
   - При недоступности AI онлайн-запись на сайте продолжает работать на 100%.
8. **SQL-статистика студии:**
   - Процедура `get_studio_stats` разделяет фактическую выручку (только `COMPLETED`) от прогнозируемой стоимости.
9. **Динамический PWA Shell:**
   - Индивидуальные метаданные (title, theme-color, apple-touch-icon, manifest.webmanifest) под каждого тенанта по его slug.
10. **Web Push и Outbox Queue:**
    - Таблица `notification_jobs` (с полями `status`, `leased_until`, `retry_count`, `idempotency_key`) и Edge Function `process-notifications`.
    - Генерация и скачивание `.ics` файлов для календаря.
11. **Preview & Live режим:**
    - Изоляция демонстрационных данных от рабочих данных владельца.
12. **Ограничение публичных запросов и бюджета LLM:**
    - Счетчики в `rate_limit_usage` предотвращают превышение квот.

## 4. Внешние зависимости и оставшиеся интеграционные проверки

Вся кодовая база, миграции, функции и логика выполнены и протестированы локально без внешних заглушек.

Для подключения к внешней производственной инфраструктуре требуются следующие credentials (шаблон подготовлен в `.env.example`):
1. **Supabase Cloud Project:**
   - `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`
   - `SUPABASE_SERVICE_ROLE_KEY`
   - *Проверка, остающаяся для внешнего контура:* Нажатие кнопки Deploy Edge Functions в облачный инстанс Supabase и запуск миграций через `supabase db push`.
2. **LLM API Key:**
   - `LLM_API_KEY` (OpenAI gpt-4o-mini или совместимый провайдер).
   - *Проверка, остающаяся для внешнего контура:* Реальный диалог с внешней LLM по сетевому API (внутренний fallback протестирован локально).
3. **VAPID Keys для Web Push:**
   - `VAPID_PUBLIC_KEY` и `VAPID_PRIVATE_KEY` (генерируются через `npx web-push generate-vapid-keys`).
   - *Проверка, остающаяся для внешнего контура:* Получение push-уведомления на реальном физическом iPhone в режиме Add to Home Screen (PWA).
